# Интеграция с 24saas.kz — BILLmanager + VMmanager

Документ заменяет гипотезы из `24saas-conversation.md` на то, что следует из
документации ISPsystem. Это рабочий план для `Saas24ApiAdapter` (Phase 2).

**Что установлено.** Кабинет 24saas — это **BILLmanager 6** (ссылка регистрации
ведёт на `cabinet.24saas.kz/billmgr`), виртуальные серверы у них на **VMmanager**.
Значит, у нас есть не один, а **два** программных интерфейса, и они решают разные
задачи:

| Слой | Что через него делаем | Документация |
|---|---|---|
| **BILLmanager** (`cabinet.24saas.kz/billmgr`) | заказ услуги, статус услуги, продление, удаление, деньги | `docs/bc/razrabotchiku/rabota-s-api/*` |
| **VMmanager** (панель, куда BILLmanager заводит нам учётку) | SSH-ключи, состояние ВМ, старт/стоп/ребут, переустановка ОС | `docs/vmmanager-admin/razrabotchiku/rabota-s-api` |

Весь план ниже построен на этом разделении.

---

## 1. Пять вопросов — что с ними стало

| Вопрос | Статус |
|---|---|
| Добавят ли наш бутстрап-рецепт | **Снят, рецепт не нужен.** См. §2 — SSH-ключ решает задачу лучше. Рецепт остаётся запасным вариантом. |
| Как получать доступ к машине | **Решено документацией.** VMmanager записывает SSH-ключи владельца ВМ из личного кабинета в `/root/.ssh/authorized_keys` при создании ВМ. Ключ регистрируется один раз, дальше он на каждой новой машине. |
| Доступен ли клиенту resume | **Проверяется скриптом**, не документацией. В справочнике BILLmanager у `vds.resume` уровень доступа admin, у `vds.suspend.confirm` — admin user. Если resume нам закрыт, запуск делаем через VMmanager API, где машина наша. |
| Сколько стоит остановленная машина | **Из документации не следует** — это их тарифная политика. Один вопрос письмом. До ответа считаем, что остановленная машина стоит как работающая. |
| VMmanager 5 или 6 | **Определяется по панели**: у 6-й версии API вида `/vm/v3/host` и `/auth/v4/...`, у 5-й — `/vmmgr?func=...`. Скрипт `vmmanager-discover.mjs` отвечает за один запуск. |

Остаётся ровно **один вопрос к людям** — про тарификацию остановленной машины.
Всё остальное выясняется запуском двух скриптов из `scripts/`.

## 2. Как сервис попадает на машину

Было (гипотеза): наш установочный скрипт как «рецепт» на их стороне. Это
требовало их администратора и не позволяло передавать переменные конкретной
компании.

Стало: **заказ через BILLmanager, установка по SSH нашим воркером.**

1. Один раз: генерируем пару ключей для платформы, публичный кладём в профиль
   SSH-ключей в VMmanager-кабинете, приватный — в `SECRETS_ENCRYPTION_KEY`-
   шифрованное хранилище платформы (`SAAS24_SSH_PRIVATE_KEY`).
2. Заказ ВМ через BILLmanager.
3. Опрос статуса услуги до `item_status=2` и непустого `ip`.
4. Воркер подключается по SSH под root с ключом, выполняет установочный скрипт
   сервиса (`installScriptRef`) и передаёт переменные компании через окружение —
   ровно то, что сегодня делает оператор руками.
5. `connection_info` запечатывается как обычно.

Почему так лучше рецепта: переменные на машину мы передаём сами, скрипт меняем
без согласования, ошибку установки видим в своём логе, а не в чужом статусе. И
главное — не нужно ждать действий администратора 24saas.

**Что проверить:** записывает ли их сборка ключи на машины, созданные через
BILLmanager (ВМ формально создаётся под учёткой клиента в VMmanager, и ключи
берутся у владельца ВМ). Это пункт 6 чек-листа §6. Если нет — остаётся рецепт.

## 3. BILLmanager: контракт

**Базовый URL:** `https://cabinet.24saas.kz/billmgr`. Метод POST,
`application/x-www-form-urlencoded`, `out=JSONdata`.

**Авторизация.** `func=auth&username=&password=` возвращает номер сессии,
дальше `auth=<id>` в каждом запросе. Сессия живёт час с последнего запроса —
клиент должен переавторизоваться и повторить запрос, а не падать.

Вариант `authinfo=логин:пароль` в каждом запросе тоже работает, но кладёт
пароль в query-строку и в логи. Используем только как аварийный.

**Ошибки.** Приходят телом `doc.error` с полем `type`, HTTP-статус при этом
может быть 200. Удаление возвращает 200, даже если записи нет. Значит:
результат операции проверяем по списку услуг, а не по коду ответа.

**Заказ.** Два пути:

- `v2.vds.order.param` + `skipbasket=on` — оплата сразу с лицевого счёта;
- корзина: `v2.vds.order.param` + `clicked_button=order` → `lineitem.id` →
  `cartorder.create.confirm&elid=<lineitem>&paymethod_id=0` → `billorder`.

Берём **второй**: на каждом шаге есть идентификатор, который можно записать до
следующего шага. Это то, на чём строится идемпотентность.

Параметры заказа: `pricelist`, `datacenter`, `order_period=1`, `ostempl`,
`addon_<id>=<значение>`, `autoprolong=on`, `domain`, `sok=ok`.

**Идемпотентность — наша, не их.** Передаём детерминированный `domain` вида
`d-<shortDeploymentId>.<наш суффикс>` и **записываем его до вызова**. Поле
`domain` возвращается в списке услуг, так что при повторе после таймаута мы
сначала ищем услугу с этим domain и заказываем только если её нет. Ключа
идемпотентности у них в документации нет, `remoteid` предназначен для
перепродающих биллингов и в списке услуг не описан.

**Статус.** `func=vds` возвращает `id`, `domain`, `ip`, `status_msg`,
`item_status`, `expiredate`, `pricelist`. Значения `item_status`: 1 — заказан,
2 — активен, 3 — приостановлен, 4 — удалён, 5 — в обработке.

Маппинг на наш `DeploymentStatus`:

| item_status | наш статус |
|---|---|
| 1, 5 | `provisioning` |
| 2, ip пустой | `provisioning` |
| 2, ip есть | `active` |
| 3 | `stopped` |
| 4 или услуга не найдена | `stopped` (и запись в лог) |

**Удаление.** `vds.delete&elid=<id>&sok=ok`, затем подтверждение по списку.

**Жизненный цикл.** `vds.suspend.confirm` (остановка, доступна клиенту),
`vds.reboot.confirm`, `vds.resume` (вероятно только админ), `vds.edit` с
`addon_*` для изменения конфигурации.

## 4. Сроки и режим ожидания

Таймаут на установку ОС в BILLmanager — 30 минут по умолчанию. При неудаче
платформа удаляет машину, делает ещё несколько попыток и затем ставит задачу
на **ручную обработку у себя**. Следствия для нас:

- опрос статуса — с интервалом порядка минуты и горизонтом в несколько часов;
- `reconcileStalledDeployments` не должен помечать `FAILED` раньше этого
  горизонта, иначе мы закажем вторую машину поверх ещё создающейся;
- долгий `item_status=5` — это, возможно, их оператор, а не наша ошибка.

## 5. Деньги и эксплуатация

- Оплата заказа идёт **с лицевого счёта**. Нужен предоплаченный баланс.
  Кончившийся баланс останавливает машины всех наших клиентов сразу, поэтому
  нужен мониторинг баланса с порогом и письмом в ops.
- Минимальный период — месяц. Почасовой тарификации в этом API нет, каждая
  тестовая машина стоит месяц.
- `autoprolong=on` обязателен: наш биллинг и их продление — разные системы.
- Наша пауза (`PAUSED` → `STOPPED`) не останавливает их тарификацию
  автоматически. Пока ответ по стоимости остановленной машины не получен,
  считаем паузу платной и не обещаем клиенту обратного.

## 6. Чек-лист запуска (минимум действий)

1. `npm run saas24:discover` — читает кабинет и пишет отчёт. **Ничего не
   меняет и не заказывает**: все запросы без `sok=ok`.
   Нужны `SAAS24_BILLMGR_USER`, `SAAS24_BILLMGR_PASSWORD`.
2. Из отчёта выписать в `.env`: `SAAS24_PRICELIST_<TIER>`, `SAAS24_DATACENTER`,
   `SAAS24_OSTEMPL`, карту `addon_*` для vcpu/ram/disk.
3. В кабинете открыть услугу → кнопку перехода в панель VMmanager, записать её
   URL.
4. `npm run saas24:vm-discover` — определяет версию VMmanager, проверяет
   авторизацию и список ВМ.
5. Добавить публичный ключ платформы в профиль SSH-ключей VMmanager.
6. `npm run saas24:spike -- --i-accept-the-charge` — заказывает **одну**
   машину, ждёт активации, пробует SSH по ключу, затем удаляет её. Это
   единственный пункт, который стоит денег (один месяц минимального тарифа).
7. Если пункт 6 зелёный — включаем `PROVIDER=saas24-api` и снимаем блокировку
   Phase 2 в `PROJECT_SPEC.md` §2 #2 и §11.

## 7. Что меняется в коде платформы

- `ProvisionResult` получает третий режим: заказано, ещё не готово
  (`automatic_pending`), плюс `externalRef` — id услуги в BILLmanager.
  Он же пишется в `VMInstance.external_ref`.
- `Deployment` получает колонку под ключ корреляции (`domain`), записываемую
  **до** обращения к провайдеру.
- Воркер получает периодический опрос `status()` для деплоев в
  `PROVISIONING`, с горизонтом из §4.
- `packages/adapters/src/saas24-api/` — клиент BILLmanager, маппинг тарифов,
  адаптер. Файл `saas24-manual.ts` остаётся: ручной путь должен работать как
  запасной, когда API недоступен.
- Логгер: добавить `authinfo`, `password`, `auth` в список редактируемых
  ключей, включая разбор query-строк.
