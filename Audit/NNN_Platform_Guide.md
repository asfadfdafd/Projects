# NNN Audit — платформа аудиторской компании (архитектура MVP+)

Из «оценщика документов» проект превращается в воронку: захват лида → мгновенный анализ → запись на платную услугу → ведение клиента в CRM. Входных каналов два (веб-форма и Telegram-бот), логика анализа общая.

## Из чего состоит платформа (4 воркфлоу + БД)

1. **NNN Analysis Engine (под-воркфлоу)** — `NNN_Analysis_Engine.json`
   Ядро анализа, вынесено отдельно, чтобы не дублировать. Принимает на вход `contract_text`, `reconciliation_text`, `currency`, `property_name` и возвращает находки, задачи, точную сумму переплаты и текст письма-претензии. Вызывается из любого канала через узел Execute Workflow.

2. **Веб-форма** — `NNN_Audit_Workflow.json` (v3, уже есть)
   Форма с загрузкой PDF → извлечение текста/OCR → анализ → письмо на email. *(Опционально можно отрефакторить, чтобы тоже звала движок — сейчас логика в ней своя.)*

3. **Telegram-бот** — `NNN_Telegram_Bot.json`
   Клиент пишет боту, присылает два PDF по очереди. Бот копит документы в буфере (`nnn_tg_intake`), как получит оба — вызывает движок, отвечает чек-листом и суммой переплаты прямо в чате и показывает кнопку «📅 Записаться на детальный аудит». Лид и анализ пишутся в CRM.

4. **Запись (Cal.com webhook)** — `NNN_Booking_Webhook.json`
   Принимает вебхук о новой брони из Cal.com, сохраняет её в `nnn_bookings`, двигает лид в статус `booked`, шлёт подтверждение клиенту и уведомление команде.

5. **CRM-схема** — `NNN_CRM_schema.sql`
   Таблицы Postgres: `nnn_leads`, `nnn_analyses`, `nnn_bookings`, `nnn_tg_intake`, `nnn_messages`.

## Схема потоков

```
ВЕБ:    Форма → (извлечение/OCR) → Движок → email
TELEGRAM: Бот ← PDF×2 → буфер(Postgres) → Движок → ответ в чате + кнопка записи → CRM
ЗАПИСЬ: Cal.com → Webhook → Postgres(bookings) → лид=booked → подтверждение клиенту + алерт команде
CRM:    leads → analyses → bookings  (единая воронка)
```

## Порядок настройки (один раз)

**1. База.** Открой `NNN_CRM_schema.sql` и выполни в своей Postgres (тот же креденшл `Social Automation DB`, что в Instagram-workflow). Создадутся 5 таблиц.

**2. Движок.** Импортируй `NNN_Analysis_Engine.json`. Привяжи во всех трёх Groq-узлах креденшл `Header Auth account`. Сохрани (активировать не нужно — он вызывается другими).

**3. Telegram-бот.**
- У @BotFather создай бота, получи токен. В n8n добавь креденшл **Telegram API** с этим токеном и выбери его во всех Telegram-узлах.
- В узлах Postgres выбери свой креденшл БД.
- В узле **«🧠 Анализ (движок)»** в поле Workflow выбери импортированный *NNN Analysis Engine*.
- В узле **«📤 Отправить результат + кнопку»** замени URL `https://cal.com/your-team/nnn-audit` на свою страницу записи.
- Активируй воркфлоу. Напиши боту — пришли два PDF.

**4. Запись (Cal.com).**
- Заведи бесплатный аккаунт на cal.com, создай тип события «NNN детальный аудит».
- Импортируй `NNN_Booking_Webhook.json`, привяжи Postgres и Gmail-креденшлы, поставь адрес команды.
- Скопируй Production URL узла Webhook и пропиши его в Cal.com → Settings → Webhooks, событие **Booking Created**.
- Активируй воркфлоу.

## Как работает накопление документов в Telegram
Бот не держит состояние в памяти — он хранит присланные тексты в таблице `nnn_tg_intake` по `chat_id`. Первый PDF помечается как `contract`, второй — `reconciliation`. Как только в буфере 2 документа, запускается анализ, а после ответа буфер очищается, чтобы следующая проверка началась заново.

## Идеи следующих шагов
- Рефакторинг веб-формы на вызов движка (единый источник правды).
- Платёж по ссылке (Stripe/Kaspi) перед записью или после неё; цена как % от выявленной переплаты.
- E-подпись engagement letter (DocuSign) после записи.
- FAQ-режим бота: отвечать на вопросы про NNN тем же Groq между загрузками.
- Напоминания о 90-дневном сроке оспаривания (Schedule Trigger + nnn_analyses).
- Дашборд для фирмы (артефакт/Metabase): выявленные переплаты, конверсия лид→запись.
- Портфельный режим: несколько объектов и лет на одного клиента.

## Замечание по тестированию
Эти три воркфлоу — рабочая основа, но их структуру я собирал без запуска в твоём n8n. После импорта прогони каждый по разу (Telegram — реальной отправкой двух PDF; запись — тестовой бронью в Cal.com) и проверь узлы Postgres/Telegram на ошибки маппинга. Если что-то не сойдётся — пришли текст ошибки конкретного узла, поправлю.
