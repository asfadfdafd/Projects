# Workflow в n8n: Автоматический аудит NNN-сверки (Triple Net Lease)

**Назначение.** Пользователь загружает два PDF — договор аренды и годовую сверку NNN-расходов (CAM / reconciliation statement). Система извлекает текст, отдаёт оба документа LLM, та находит ошибки и завышения, и пользователь получает на email понятный чек-лист задач с приоритетами.

**Ключевой принцип.** Результат пишется для обычного арендатора, а не для аудитора. Никакого профессионального жаргона без расшифровки, каждая задача — это конкретное действие («попросите арендодателя прислать…»), а не аудиторский термин.

---

## 1. Общая схема (поток узлов)

```
[1. Форма загрузки PDF]
        │
        ▼
[2. Разделение файлов]  ──► (договор / сверка)
        │
        ├──► [3a. Извлечь текст: Договор]
        └──► [3b. Извлечь текст: Сверка]
        │
        ▼
[4. Объединить тексты (Merge)]
        │
        ▼
[5. Подготовить данные для LLM (Set/Code)]
        │
        ▼
[6. LLM-анализ NNN (AI / OpenAI node)]
        │
        ▼
[7. Распарсить ответ (Code — JSON в объекты)]
        │
        ▼
[8. Сформировать HTML-письмо (чек-лист)]
        │
        ▼
[9. Отправить Email пользователю]
        │
        ▼
[10. Экран «Готово» для пользователя]
```

---

## 2. Пошаговое описание узлов

### Узел 1 — «📥 Форма: загрузка двух PDF»
**Тип:** `Form Trigger` (n8n Forms).
**Зачем:** точка входа. Простая веб-форма, которую можно дать любому сотруднику — не нужен доступ к n8n.

Настройки:
- **Form Title:** «Проверка NNN-расходов».
- **Form Description:** «Загрузите договор аренды и годовую сверку расходов. Мы найдём возможные ошибки и пришлём список задач на email.»
- Поля:
  1. `Ваш email` — тип **Email**, обязательное. Сюда придёт отчёт.
  2. `Договор аренды (PDF)` — тип **File**, accept `.pdf`, обязательное.
  3. `Годовая сверка NNN (PDF)` — тип **File**, accept `.pdf`, обязательное.
  4. `Название объекта / адрес` — тип **Text**, необязательное (для красоты письма).
- **Respond:** «Using 'Respond to Webhook' node» — чтобы в конце показать экран «Готово».

> 💬 *Комментарий узла:* «Единая точка входа для пользователя. Принимает два файла и email. Не требует знаний n8n.»

---

### Узел 2 — «🗂 Разделение: договор и сверка»
**Тип:** `Set` (или `Edit Fields`).
**Зачем:** в форме файлы приходят как `binary` свойства (например `Договор аренды (PDF)` и `Годовая сверка NNN (PDF)`). Нормализуем их в понятные имена `contract_pdf` и `reconciliation_pdf`, чтобы дальше не путаться.

- Включить **Keep Only Set / Include Binary**: переименовать бинарные ключи в `contract_pdf` и `reconciliation_pdf`.
- Сохранить `email` и `property_name` как поля.

> 💬 *Комментарий:* «Приводим имена файлов к стандартным, чтобы две ветки извлечения текста не перепутали документы.»

---

### Узлы 3a / 3b — «📄 Извлечь текст: Договор» и «📄 Извлечь текст: Сверка»
**Тип:** `Extract from File` (Operation: **Extract from PDF**).
**Зачем:** превращаем PDF в текст для LLM.

- Узел 3a: **Input Binary Field** = `contract_pdf` → результат в поле `contract_text`.
- Узел 3b: **Input Binary Field** = `reconciliation_pdf` → результат в поле `reconciliation_text`.

> ⚠️ Если сверка приходит сканом (картинкой), Extract from PDF вернёт пустой текст. На этот случай заложите ветку OCR (узел `HTTP Request` к OCR-сервису или Mistral OCR / Google Vision). Для MVP достаточно текстовых PDF.

> 💬 *Комментарий:* «Извлекаем текст отдельно из каждого документа. Если текст пустой — вероятно скан, нужен OCR.»

---

### Узел 4 — «🔗 Объединить тексты»
**Тип:** `Merge` (Mode: **Combine** → **Combine by Position**), либо проще — собрать оба текста через `Set`, ссылаясь на оба предыдущих узла.
**Зачем:** свести `contract_text` и `reconciliation_text` в один элемент, чтобы передать LLM целиком.

> 💬 *Комментарий:* «Собираем оба текста в один объект для единого запроса к ИИ.»

---

### Узел 5 — «🧠 Собрать запрос к Groq»
**Тип:** `Code` (JavaScript).
**Зачем:** тот же приём, что в Instagram Retail workflow — формируем prompt и кладём готовое тело запроса (JSON-строку) в поле `body`, которое потом уйдёт в HTTP-узел. Здесь же обрезаем тексты под контекст модели.

Ключевые моменты тела запроса (как в примере): `model: "llama-3.1-8b-instant"`, `temperature: 0.2`, плюс `response_format: { type: "json_object" }` для строгого JSON, и `messages` с system+user. Системный промпт — см. раздел 3. Полный код — в файле `NNN_Audit_Workflow.json` (узел «🧠 Собрать запрос к Groq»).

> ⚠️ `llama-3.1-8b-instant` подходит для коротких договоров. Для длинных документов в том же Groq API поставьте более ёмкую модель `llama-3.3-70b-versatile` (увеличьте и лимит обрезки текста). Менять нужно только строку `model` — API и креденшл остаются те же.

> 💬 *Комментарий:* «Формируем prompt и кладём тело запроса в поле body — точно как в Instagram-workflow.»

---

### Узел 6 — «🤖 Call Groq AI»
**Тип:** `HTTP Request` — **тот же ИИ и тот же API, что в загруженном Instagram-workflow.**
**Зачем:** ядро — сравнивает договор и сверку.

Настройки (1:1 с примером):
- **Method:** POST
- **URL:** `https://api.groq.com/openai/v1/chat/completions`
- **Authentication:** Generic Credential Type → **Header Auth** → креденшл `Header Auth account` (заголовок `Authorization: Bearer <ваш GROQ_API_KEY>`).
- **Send Body:** on, **Specify Body:** JSON, **JSON Body:** `={{ $json.body }}`
- **On Error:** Continue (continueRegularOutput).

> 💬 *Комментарий:* «Тот же Groq endpoint и тот же креденшл Header Auth, что в Instagram-workflow.»

---

### Узел 7 — «📦 Распарсить ответ ИИ»
**Тип:** `Code`.
**Зачем:** достать JSON из `choices[0].message.content` (как в Instagram-workflow «Parse AI Response»), снять markdown-обёртку, отсортировать задачи по приоритету. Если ответ не распарсился — отдаём дружелюбную задачу «пришлите текстовый PDF» вместо падения. Полный код — в JSON-файле (узел «📦 Распарсить ответ ИИ»).

> 💬 *Комментарий:* «Парсим choices[0].message.content, сортируем задачи по приоритету, ошибку парсинга превращаем в понятную задачу.»

---

### Узел 8 — «✉️ Собрать письмо (HTML-чек-лист)»
**Тип:** `Code` или `HTML`.
**Зачем:** сделать красивое и понятное письмо: краткий вывод, сумма возможной переплаты, чек-лист задач с цветными приоритетами.

Пример (Code → возвращает поле `html`):
```javascript
const d = $json;
const color = { 'Высокий':'#e53935','Средний':'#fb8c00','Низкий':'#43a047' };
const tasks = (d.tasks || []).map((t,i)=>`
  <tr>
    <td style="padding:8px;border-bottom:1px solid #eee;">☐</td>
    <td style="padding:8px;border-bottom:1px solid #eee;">
      <span style="background:${color[t.priority]||'#999'};color:#fff;padding:2px 8px;border-radius:10px;font-size:12px;">${t.priority}</span>
    </td>
    <td style="padding:8px;border-bottom:1px solid #eee;">
      <b>${t.title}</b><br>
      <span style="color:#555;font-size:14px;">${t.what_to_do}</span>
      ${t.potential_overcharge ? `<br><span style="color:#e53935;">💰 Возможная переплата: ${t.potential_overcharge}</span>` : ''}
    </td>
  </tr>`).join('');

const html = `
<div style="font-family:Arial,sans-serif;max-width:680px;margin:auto;">
  <h2>Результаты проверки NNN — ${d.property_name||''}</h2>
  <p style="background:#f5f7fa;padding:14px;border-radius:8px;">${d.summary||''}</p>
  ${d.total_potential_overcharge ? `<p style="font-size:18px;"><b>💰 Итого возможная переплата: ${d.total_potential_overcharge}</b></p>`:''}
  <h3>Ваш список задач</h3>
  <table style="width:100%;border-collapse:collapse;">
    <tr style="background:#fafafa;"><th style="text-align:left;padding:8px;">✓</th><th style="text-align:left;padding:8px;">Приоритет</th><th style="text-align:left;padding:8px;">Что сделать</th></tr>
    ${tasks}
  </table>
  <p style="color:#999;font-size:12px;margin-top:20px;">Сформировано автоматически ${d.generated_at}. Это предварительный анализ, не юридическая консультация.</p>
</div>`;
return [{ json: { ...d, html } }];
```

> 💬 *Комментарий:* «Превращаем находки ИИ в наглядное письмо с чек-боксами и цветными приоритетами. Язык — для обычного арендатора.»

---

### Узел 9 — «📤 Отправить Email» (Gmail)
**Тип:** `Gmail` (вход через Google — без SMTP-портов и паролей приложений).
**Зачем:** доставить отчёт пользователю.

Как настроить отправку:
1. В узле «📤 Отправить Email пользователю» → Credentials → **Create New** → выбери **Gmail OAuth2** → **Sign in with Google** → разреши доступ. Тот же креденшл (`Gmail account`) привяжи к узлу «📨 Алерт аудиторской команде».
2. В узле алерта в поле **Send To** поставь реальный адрес команды вместо `audit-team@your-domain.com`.
3. Готово. Адрес получателя в письме пользователю (`{{ $json.email }}`) берётся из формы автоматически. К письму прикладывается вложение `dispute_letter` (письмо-претензия).

> ⚠️ На локальном (self-hosted) n8n кнопка «Sign in with Google» требует один раз настроить Google OAuth (создать OAuth client в Google Cloud Console и вписать Client ID/Secret в креденшл n8n) — n8n покажет нужный redirect URL. На n8n Cloud это один клик. Если настройка OAuth неудобна — альтернатива: сервис Brevo/SendGrid (узел с одним API-ключом, без портов).

> 💬 *Комментарий:* «Отправляем готовый чек-лист и вложение через Gmail на email из формы.»

---

### Узел 10 — «✅ Экран Готово»
**Тип:** `Respond to Webhook` / `Form Ending`.
**Текст:** «Готово! Мы проанализировали документы и отправили список задач на ваш email. Проверьте почту через пару минут.»

> 💬 *Комментарий:* «Подтверждение пользователю прямо в браузере, чтобы он не ждал в неведении.»

---

### Доп. узел — «⚠️ Обработка ошибок»
Подключите **Error Trigger** в отдельном workflow или ветку `IF` после узла 7 на случай `parse_error`, чтобы пользователю всё равно ушло письмо «не удалось распознать документ, пришлите текстовый PDF».

## 3. Системный промпт для LLM-узла

Скопируйте целиком в поле **System Prompt** узла 6.

```
Ты — помощник по проверке счетов за аренду коммерческой недвижимости с условиями Triple Net (NNN / NNN-lease). Твоя аудитория — обычные арендаторы (владельцы магазинов, кафе, офисов), а НЕ профессиональные аудиторы. Объясняй всё простым языком, без жаргона; если используешь термин (CAM, gross-up, base year, cap, pro-rata share), сразу давай короткое пояснение в скобках.

ТВОЯ ЗАДАЧА
Тебе дают два документа: (1) текст договора аренды и (2) текст годовой сверки NNN-расходов (reconciliation / CAM statement). Сравни их и найди возможные ошибки, несоответствия и завышения, из-за которых арендатор мог переплатить.

НА ЧТО ОБРАЩАТЬ ВНИМАНИЕ
1. Доля арендатора (pro-rata share): совпадает ли процент в сверке с процентом/площадью в договоре. Частая ошибка — завышенный процент.
2. Запрещённые к перевыставлению расходы: проверь, не включены ли в сверку статьи, которые по договору НЕ оплачивает арендатор (капитальный ремонт/capital expenditures, износ/depreciation, проценты по кредиту арендодателя, расходы на привлечение новых арендаторов, юруслуги по спорам, управленческое вознаграждение сверх лимита, налог на прибыль арендодателя).
3. Лимиты (caps): есть ли в договоре потолок роста расходов (например, controllable expenses cap 5% в год) и не превышен ли он в сверке.
4. Базовый год / стоп-расходы (base year): правильно ли вычтена база.
5. Gross-up: если здание заполнено не полностью, корректно ли расходы пересчитаны (но не завышены).
6. Управленческая комиссия (management fee): не превышает ли оговорённый процент; не начислена ли комиссия на статьи, которые сами являются комиссиями.
7. Двойной учёт: одна и та же статья дважды; налоги или страховка, посчитанные и в base rent, и в NNN.
8. Арифметика: суммы статей должны сходиться с итогом; итог × доля арендатора = выставленная сумма.
9. Сроки: выставлена ли сверка в срок, предусмотренный договором; не истёк ли срок на оспаривание.
10. Предоплаты (estimates): вычтены ли уже уплаченные ежемесячные авансы из итога.

ПРАВИЛА
- Опирайся ТОЛЬКО на текст документов. Если данных не хватает для вывода — не выдумывай, а сформулируй это как задачу «запросить документ/уточнение».
- Для каждой находки по возможности оцени сумму возможной переплаты (если в тексте есть цифры). Если посчитать нельзя — пиши «требует уточнения».
- Каждая задача — это конкретное действие для арендатора, а не наблюдение. Плохо: «Доля завышена». Хорошо: «Попросите арендодателя письменно подтвердить расчёт вашей доли — в договоре указано 4,2%, а в сверке применено 5,1%».
- Приоритеты: «Высокий» — крупные деньги или явное нарушение договора; «Средний» — вероятная ошибка, нужна проверка; «Низкий» — мелочь или формальность.
- Тон спокойный и поддерживающий. Не обвиняй арендодателя в мошенничестве — говори «возможная ошибка», «стоит уточнить».

ФОРМАТ ОТВЕТА
Верни СТРОГО валидный JSON без markdown и без текста вокруг, по схеме:
{
  "property_name": "строка",
  "summary": "2-3 предложения простым языком: что проверили и главный вывод",
  "total_potential_overcharge": "например '≈ $4 200' или 'требует уточнения'",
  "findings": [
    {
      "issue": "краткое описание проблемы простым языком",
      "evidence_contract": "что сказано в договоре (цитата/пересказ)",
      "evidence_reconciliation": "что в сверке",
      "potential_overcharge": "сумма или 'требует уточнения'"
    }
  ],
  "tasks": [
    {
      "title": "короткое название задачи",
      "what_to_do": "пошагово и просто, что именно сделать арендатору",
      "priority": "Высокий | Средний | Низкий",
      "potential_overcharge": "сумма или ''"
    }
  ]
}

Если документ нечитаем или это не договор/сверка — верни tasks с одной задачей: попросить корректный текстовый PDF, и summary с пояснением.
```

## 5. Применённые улучшения (версия v2)

Воркфлоу обновлён до v2 — ниже что изменилось и зачем. Все эти узлы уже есть в `NNN_Audit_Workflow.json`.

**1. Контроль качества PDF (защита от сканов).** Новый узел «🔎 Контроль качества PDF» считает длину извлечённого текста по каждому документу. Если текста меньше ~200 символов — это почти наверняка скан-картинка или пустой файл. Тогда ветка `FALSE` узла «❓ Документы читаемы?» отправляет пользователю понятное письмо с инструкцией «как сделать текстовый PDF», а не скармливает мусор модели. Это экономит токены и не выдаёт ложный анализ.

**2. Более сильная модель.** Заменил `llama-3.1-8b-instant` на `llama-3.3-70b-versatile` (тот же Groq API и тот же креденшл). 70B заметно точнее на юридических текстах и длинных договорах, контекст до 128k. Лимит обрезки текста поднят до 35 000 символов на документ.

**3. Надёжность вызова ИИ.** На узле «🤖 Call Groq AI» включены ретраи (3 попытки с паузой 3 сек) и таймаут 60 сек — временные сбои/перегрузки API больше не роняют прогон.

**4. Грациозная обработка ошибок парсинга.** Если модель вернула не-JSON, узел «📦 Распарсить ответ ИИ» не падает, а формирует мягкое сообщение «требуется ручная проверка» и помечает задачу высоким приоритетом, чтобы команда вмешалась.

**5. On Error = Continue на извлечении PDF и отправке.** Битый файл или сбой почты не обрывают всю цепочку.

**6. Уверенность анализа (confidence).** Модель теперь возвращает поле `confidence` (0–1), оно показывается в письме как «Уверенность анализа: NN%». Пользователь видит, насколько результату можно доверять.

**7. Валюта.** В форму добавлено поле валюты (USD/KZT/EUR). Оно прокидывается в промпт, и все суммы переплат выводятся в правильной валюте.

**8. Алерт внутренней команде.** После отправки письма узел «🚨 Есть задачи высокого приоритета?» проверяет число критичных находок. Если они есть — «📨 Алерт аудиторской команде» шлёт письмо вашей команде (это тёплый лид на платную детальную проверку/претензию). Адрес команды задайте в узле.

**9. Усиленный дисклеймер.** В письме явно сказано, что это предварительный анализ, не юр-консультация, и перед спором нужно сверяться с оригиналами.

**10. UX-мелочи.** Экран «Готово» напоминает проверить папку «Спам»; тема письма содержит число найденных задач и объект.

### Схема v2 (поток)
```
Форма → Сохранить мета → [Договор / Сверка] → Merge → Контроль качества → IF читаемы?
   ├─ TRUE  → Собрать запрос → Groq(ретраи) → Парсинг → HTML → Отправить ┐
   └─ FALSE → Письмо «нужен текстовый PDF» ─────────────────────────────→ Отправить
                                                          Отправить → ├─ IF высокий приоритет? → Алерт команде
                                                                       └─ Экран «Готово»
```

## 6. Версия v3: OCR для сканов и письмо-претензия (встроено)

**OCR для сканов.** Если «🔎 Контроль качества PDF» видит, что текст не извлёкся (скан/картинка), ветка `FALSE` идёт не в тупик, а в узлы «🔠 OCR: Договор» → «🔠 OCR: Сверка» (HTTP-запросы к **OCR.space**), затем «🧩 Собрать OCR-текст» приводит распознанный текст к общему формату и вливается в тот же анализ. В письме клиенту при этом появляется пометка «документы распознаны из скана, возможны неточности».
- Что настроить: получите ключ на ocr.space (есть бесплатный тариф) и впишите его вместо `YOUR_OCRSPACE_API_KEY` в обоих OCR-узлах (заголовок `apikey`). Язык распознавания задан `rus` — поменяйте при необходимости (`eng`, `kaz` и т.п.). Бесплатный тариф имеет лимиты на размер/страницы — для больших сканов нужен платный ключ или другой OCR (Google Vision, Mistral OCR).

**Письмо-претензия арендодателю.** После анализа делается второй вызов Groq (узлы «🧠 Запрос: письмо-претензия» → «🤖 Call Groq AI (письмо)» → «📦 Подготовить письмо-претензию»). На вход — найденные `findings`, на выходе — готовый деловой текст официальной претензии. Он прикладывается к письму клиента **вложением** `Pretenziya_arendodatelyu.txt` и показывается секцией прямо в письме. В тексте оставлены плейсхолдеры `[Арендодатель]`, `[Арендатор]`, `[Дата]` — клиент подставляет свои данные. Письмо генерируется только если есть находки (`has_findings`).

### Полная схема v3
```
Форма → Мета → [Договор/Сверка] → Merge → Контроль качества → IF текст извлечён?
  ├─ TRUE  ───────────────────────────────────┐
  └─ FALSE → OCR Договор → OCR Сверка → Собрать OCR ┘
        → Собрать запрос → Groq(анализ) → Парсинг
        → Запрос письма → Groq(письмо) → Подготовить письмо
        → HTML → Отправить клиенту → ├─ IF высокий приоритет → Алерт команде
                                      └─ Экран «Готово»
```
