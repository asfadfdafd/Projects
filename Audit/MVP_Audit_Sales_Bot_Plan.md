**Версия:** 1.0 (черновик на согласование)
**Дата:** 12.06.2026
**Статус:** ожидает утверждения перед началом разработки

## 0. Зачем этот документ

Поступила уточнённая постановка от руководителя. Она **меняет суть продукта**: то, что сейчас лежит в папке, — это инструмент анализа NNN-сверки (находит переплаты арендатора по документам). Новая задача — **воронка продаж аудиторской фирмы**: Instagram + чат-бот, который консультирует, собирает анкету, считает цену, выкатывает КП и доводит клиента до подписания договора. Сам аудит в MVP не трогаем.

Ниже: что меняется, что переиспользуем, целевая схема, модель данных, этапы и что нужно от вас.

---

## 1. Бизнес-процесс MVP (7 шагов руководителя)

1. **Точка входа** — клиент приходит из Instagram в чат-бот.
2. **Консультация (FAQ)** — бот отвечает на вопросы: стоимость, виды аудита, наличие лицензии (например, для недропользователей) и пр.
3. **Инициация заказа** — клиент говорит «хочу заказать аудит».
4. **Анкетирование** — бот отправляет анкету (бриф) и переходит в режим ожидания.
5. **Генерация КП** — система анализирует возвращённую анкету и рассчитывает стоимость.
6. **Оформление** — при согласии бот генерирует и отправляет договор на подписание.
7. **Граница MVP** — автоматизация завершается **до** начала фактического аудита. Загрузка документов и выдача рекомендаций — следующие этапы.

## 2. Утверждённые решения (из уточняющих вопросов)

| Вопрос | Решение |
|---|---|
| Каналы | **Telegram + Instagram Direct** (оба), общий бэкенд |
| Расчёт цены (КП) | **Гибрид**: правила считают число, LLM пишет текст КП |
| Договор + подпись | **Авто-PDF + ссылка на э-подпись** (DocuSign/SignNow и т.п.) |
| Анкета | **Предоставит заказчик** — под её поля настраиваем прайс-логику |

## 3. Что переиспользуем, что меняем, что откладываем

**Переиспользуем как есть (или с мелкой правкой):**
- Postgres + креденшл БД — основа CRM.
- Каркас Telegram-бота (`NNN Telegram Bot…`) — приём сообщений, ответ в чат, кнопки.
- Креденшл Groq (`Header Auth account`) — для FAQ и текста КП.
- Gmail-узлы — уведомления команде и клиенту.
- Cal.com-вебхук — опционально, для записи на консультацию с аудитором.

**Перепрофилируем (логика меняется, узлы-«кирпичи» остаются):**
- Буфер `nnn_tg_intake` (накопление файлов) → **накопление/ожидание анкеты** и состояние диалога.
- «Analysis Engine» (сравнение договор↔сверка) → **движок ценообразования** (анкета → цена + текст КП). Узлы Groq + Code переиспользуются, промпты и формулы новые.

**Откладываем на Фазу 3+ (это и есть «сам аудит»):**
- NNN-анализ переплат, OCR, письмо-претензия. Не удаляем — паркуем как задел для платного этапа после подписания.

> Вывод: значительная часть инфраструктуры (БД, бот, Groq, почта) переиспользуется. Меняются **промпты, формулы цены, схема диалога и модель данных**.

## 4. Целевая архитектура

```
INSTAGRAM ─┐                                  ┌─ Email/уведомления команде
           ├─► [Адаптер канала] ─► [Ядро диалога: state machine] ─┤
TELEGRAM  ─┘                              │                       └─ CRM (Postgres)
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                ▼                 ▼                ▼                  ▼
   [FAQ/Groq]    [Инициация заказа]  [Приём анкеты]  [Движок цены]    [Договор+э-подпись]
   база знаний   детект намерения    парсинг полей   правила+LLM КП    шаблон PDF → ссылка
```

**Ключевые компоненты:**

1. **Адаптеры каналов.** Telegram (готов) и Instagram Direct через Meta Messaging API. Оба нормализуют входящее сообщение в единый формат `{channel, user_id, text, attachments}` и шлют в ядро. Один бэкенд — две «трубы».

2. **Ядро диалога (state machine).** Бот без памяти в ОЗУ: состояние клиента хранится в БД (как сейчас сделан буфер Telegram). Состояния: `greeting → faq → order_intent → awaiting_questionnaire → pricing → proposal_sent → negotiating → contract_sent → signed → handoff`. На каждое сообщение ядро смотрит текущее состояние и решает, какой блок вызвать.

3. **FAQ-консультант.** Groq отвечает на вопросы о ценах/видах/лицензиях, опираясь на **базу знаний услуг** (мы её заполняем из материалов аудитора), а не выдумывает. Детектит фразу-намерение «хочу заказать» → переводит в `order_intent`.

4. **Анкетирование.** Бот отправляет анкету (ссылку на форму или вопросы по шагам), ставит состояние `awaiting_questionnaire`, ждёт. Принимает заполненную анкету, парсит поля.

5. **Движок цены (гибрид).** Code-узел считает цену **детерминированно** по прайс-матрице (вид аудита × размер компании × выручка × лицензия недропользователя × срочность и т.д.). Groq затем оборачивает число в человеческий текст КП. **Цену определяют правила, не LLM.**

6. **Договор + э-подпись.** При согласии — генерация PDF из шаблона (поля клиента + цена) и отправка ссылки на подпись через э-подпись провайдера. Вебхук провайдера ловит факт подписания → состояние `signed` → алерт команде.

7. **CRM/уведомления.** Каждый шаг пишется в Postgres; на ключевых событиях (новый лид, согласие на КП, подписание) — письмо/сообщение команде.

## 5. Изменения модели данных (Postgres)

Существующие таблицы переиспользуем/расширяем, добавляем новые:

- `leads` (из `nnn_leads`) — добавить `channel` (telegram/instagram), `state` (текущее состояние диалога), контактные данные.
- `conversations` / `messages` (из `nnn_messages`) — история по каналам, для контекста FAQ.
- `services` (новая) — каталог услуг: вид аудита, описание, базовая цена/диапазон.
- `pricing_rules` (новая) — коэффициенты и правила (множители по выручке, штату, лицензии, срочности).
- `questionnaire_responses` (новая) — разобранные поля анкеты по лиду.
- `proposals` (новая) — КП: рассчитанная цена, текст, статус (sent/accepted/declined).
- `contracts` (новая) — ссылка на PDF, статус подписи, дата, external_id провайдера.
- `bookings` (`nnn_bookings`) — оставляем для опциональной записи на консультацию.

Финальные поля `questionnaire_responses` и `pricing_rules` фиксируем **после получения анкеты** от вас.

## 6. Что нужно от вас (блокеры разработки)

1. **Анкета (бриф)** — тот файл, что упоминал руководитель. Без него нельзя зафиксировать поля и формулу цены.
2. **Каталог услуг и логика цены** — виды аудита, базовые цены/диапазоны (300k / 500k / 1 000 000 и от чего зависит), скидки/надбавки.
3. **Данные о лицензиях** — что писать в FAQ (например, лицензия на аудит недропользователей).
4. **Meta/Instagram** — бизнес-аккаунт Instagram + доступ к Meta Developer для Messaging API (нужно ревью Meta — закладываем время).
5. **Провайдер э-подписи** — выбрать (DocuSign / SignNow / др.) и дать аккаунт/ключ.
6. **Шаблон договора** — текст для генерации PDF (с плейсхолдерами под имя, цену, дату).

## 7. Этапы поставки

**Фаза 0 — фундамент (общий бэкенд).**
Модель данных, state machine, база знаний для FAQ, единый формат сообщений. Узлы Postgres из текущих воркфлоу переиспользуем.

**Фаза 1 — сквозной MVP в Telegram (быстрая проверка ценности).**
FAQ → инициация → анкета → расчёт цены → КП → договор → э-подпись, всё на Telegram. Telegram-first, потому что не требует ревью Meta — даёт работающий продукт раньше.

**Фаза 2 — подключение Instagram Direct.**
Тот же бэкенд, добавляем адаптер Meta Messaging API. Параллельно идёт ревью Meta-приложения.

**Фаза 3 — отложенное (после MVP).**
Загрузка документов клиентом, фактический аудит (переиспользуем припаркованный NNN-движок/OCR/претензию), выдача рекомендаций, оплата по ссылке, дашборд по воронке.

---

## 8. Риски и как снижаем

- **Instagram-автоматизация** требует одобрения Meta (бизнес-аккаунт + App Review) — может занять время. Снижаем: Telegram-first (Фаза 1 не зависит от Meta).
- **Точность цены** — целиком на правилах и анкете; LLM пишет только текст, не число. Перед запуском прогоняем матрицу на реальных примерах от аудитора.
- **Юридическая сила договора/э-подписи** — шаблон и провайдера согласовать с юристом аудитора; в КП и письмах дисклеймер.
- **Воркфлоу из VM пока не протестированы** (отмечал руководитель) — на Фазе 0 прогоняем каждый узел, чиним маппинги, заполняем плейсхолдеры (OCR-ключ, e-mail команды, Cal.com URL).
