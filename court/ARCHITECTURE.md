# Архитектура и обоснование решений

Документ отвечает на вопросы, которые задают после демонстрации:
почему выбрана такая модель, что с конфиденциальностью, и что придётся
изменить при переходе к реальной эксплуатации.

---

## 1. Общая схема

```
   txt · docx · rtf · pdf · скан
               │
               ▼
      ┌──────────────────┐
      │  documents.py    │   разбор формата, цепочка запасных вариантов
      └────────┬─────────┘
               ▼
      ┌──────────────────┐
      │   Extractor      │   интерфейс: rule_based_offline | llm
      │  извлечение      │   каждый признак -> цитата-основание
      └────────┬─────────┘
               │  структурированная карточка дела
      ┌────────┴───────────────────────────┬────────────────────────┐
      ▼                                    ▼                        ▼
┌──────────────┐               ┌──────────────────────┐   ┌──────────────┐
│  features.py │               │ judge_analysis       │   │   правки     │
│  вектор      │               │  спорные точки,      │   │ пользователя │
└──────┬───────┘               │  хронология, вопросы │   └──────┬───────┘
       │                       │         ▲            │          │
       ├───────────────┐       │  contradictions.py   │          │
       ▼               ▼       │  расхождения сторон  │          │
┌──────────────┐ ┌───────────┐ └──────────┬───────────┘          │
│ predictor.py │ │ similar_  │            │                      │
│ вероятность, │ │ cases.py  │            │                      │
│ сумма,       │ │ похожие   │            │                      │
│ объяснение   │ │ дела      │            │                      │
└──────┬───────┘ └─────┬─────┘            │                      │
       │◄──────────────┘◄─────────────────┼──────────────────────┘
       ▼                                  ▼
Модуль 1 (гражданин)               Модуль 2 (судья)
вероятность, ожидаемое             обзор, расхождения, вопросы
взыскание, факторы, аналоги        БЕЗ вероятности исхода
```

Ядро (`core/`) не знает ни о HTTP, ни о вебе. `app.py` — тонкий слой
маршрутизации; замена его на FastAPI (см. `app_fastapi.py`) не затрагивает
логику.

## 2. Почему логистическая регрессия

Требование объяснимости в судебной сфере не «желательное», а профильное:
вывод, который нельзя проверить, здесь неприменим независимо от точности.

| | Логистическая регрессия | Градиентный бустинг | Нейросеть |
|---|---|---|---|
| ROC-AUC на этих данных | **0,824** | 0,819 | не обучалась |
| Вклад признака | считается **точно**: `коэф. × значение` | аппроксимация (SHAP) | аппроксимация |
| Время обучения | секунды | секунды | часы + разметка |
| Объём выгрузки | 6 КБ JSON | сотни деревьев | десятки МБ |

Бустинг обучается в том же скрипте именно для того, чтобы этот выбор был
измеренным, а не декларативным: разница в 0,004 ROC-AUC не окупает потерю
точной объяснимости. Если на реальных данных разрыв окажется существенным,
решение пересматривается — код сравнения уже на месте.

Рядом работает вторая, отдельная модель — гребневая регрессия доли
удовлетворённых требований, обученная только на выигранных делах.
Разделение намеренное: «удовлетворят ли иск» и «в каком объёме» — разные
вопросы с разными предикторами, и смешивать их в одной модели значило бы
ухудшить обе. Ожидаемое взыскание считается как произведение вероятности,
предсказанной доли и заявленной суммы.

Отдельно: **калибровка важнее точности**. Пользователю показывается число
в процентах, и оно должно означать ровно то, что означает. Поэтому в
метриках есть Brier score и калибровочная таблица, а в интерфейсе —
диапазон оценки шириной 5,0 п.п., равный фактическому расхождению
прогноза с частотой исходов на проверочной выборке.

Отдельный способ проверки, доступный пользователю без знания статистики:
рядом с оценкой показываются похожие дела из базы и доля выигранных среди
них. Она считается простым подсчётом, а не моделью, — и на демо-делах
сходится с прогнозом (91 % против 93 %, 2 % против 0 %). Расхождение этих
двух чисел было бы поводом не доверять модели.

## 3. Извлечение признаков: почему правила, а не LLM

Выбран полностью офлайн-режим, поэтому в демо работает
`RuleBasedExtractor`: ключевые слова, обработка отрицаний, разбор дат
и сумм. Ни одного сетевого вызова в коде нет.

Практическая деталь, которая важнее, чем кажется: **обработка отрицаний
обязательна**. Фраза «трудовой договор мне на руки не выдавался» без неё
засчитывается как наличие договора и завышает оценку шансов.
Ложноположительное срабатывание здесь опаснее пропуска, поэтому каждый
признак-доказательство проверяется на отрицание в окне ±130 символов
(`core/extraction.py`, список `NEGATIONS`, автотест в `smoke_test.py`).

`LLMExtractor` реализует тот же интерфейс и подключается переменной
окружения `EXTRACTOR`. Ожидаемый контракт: модель возвращает строгий JSON
по схеме `core/schema.py`, после чего результат проходит ту же валидацию,
что и правиловый вывод. При появлении в контуре локальной модели
(llama.cpp / Ollama / vLLM) меняется одна строка конфигурации.

Компенсация текущих ограничений — в интерфейсе: каждый признак
сопровождается цитатой-основанием и правится пользователем с немедленным
пересчётом оценки.

## 4. Конфиденциальность

Материалы дела — чувствительные данные. В демо заложены следующие свойства,
и все они проверяемы по коду:

| Свойство | Как обеспечено |
|---|---|
| Данные не покидают контур | Исходящих сетевых вызовов в коде нет вообще. Интерфейс не подключает CDN и внешние шрифты |
| Недоступность извне | Сервер слушает только `127.0.0.1` |
| Нет следов на диске | Тексты обрабатываются в памяти, не сохраняются, не кешируются |
| Нет утечки в журнал | В лог пишутся только метод и путь; содержимое документов — никогда |
| Минимальная поверхность атаки | Нулевые внешние зависимости у рантайма; статика отдаётся с проверкой выхода за пределы каталога |

Чего в демо **нет** и что обязательно для эксплуатации: аутентификация и
разграничение доступа, шифрование хранилища, журнал действий
пользователей, обезличивание персональных данных перед обработкой,
регламент хранения и удаления. Это осознанный объём демо, а не упущение,
и его следует называть прямо.

## 5. Дообучение на исходах рассмотренных дел

Требование «система должна учиться на результатах» заложено в архитектуру,
хотя сам цикл в демо не запускается.

Как это работает:

1. **Схема — один источник правды.** `core/schema.py` описывает признаки;
   генератор, обучение, извлечение и интерфейс читают её оттуда.
   Добавление признака — правка в одном месте.
2. **Единый код признаков для обучения и инференса.** `features.py`
   используется обоими путями, поэтому расхождение train/serve
   исключено конструктивно. При загрузке модель сверяет список признаков
   с сохранённым в `model.json` и отказывается работать при несовпадении.
3. **Накопление исходов.** Фактический результат рассмотренного дела
   дописывается в `data/cases.csv` (колонки `outcome_win`,
   `satisfied_share`, `outcome_label`). Реальные записи отличаются от
   синтетических тем, что у них нет `true_probability`.
4. **Переобучение — одна команда.** `python3 scripts/train_model.py`
   заново обучает модель, пересчитывает метрики и калибровку и
   перезаписывает `models/model.json` с полем `model_version`.
5. **Контроль качества смены версии.** Метрики каждой версии остаются в
   `models/metrics.json`; калибровочная таблица показывает, не разъехались
   ли вероятности после дообучения.

Что нужно достроить для практики: хранилище исходов вместо CSV, версионирование
артефактов модели с возможностью отката, автоматическая проверка, что новая
версия не хуже предыдущей на отложенной выборке, и отслеживание сдвига
распределения (изменения практики со временем).

## 6. Что делать при переходе на реальные данные

По убыванию важности:

1. **Собрать корпус исходов.** Минимально осмысленно — несколько тысяч
   дел с признаками и результатами. Это главный ограничитель, а не
   вычислительные мощности и не выбор модели.
2. **Проверить смещения.** Модель, обученная на исторических решениях,
   воспроизводит и их систематические перекосы. Нужен анализ по составу
   сторон, категориям и судам, прежде чем показывать числа пользователям.
3. **Перепроверить калибровку на реальных данных.** Синтетическая
   калибровка ничего не говорит о настоящей.
4. **Проверить разбор PDF на реальных файлах.** Встроенный разборщик и
   pypdf покрывают текстовые PDF; для сканов нужен tesseract в контуре.
5. **Развернуть локальную языковую модель** для извлечения признаков,
   сохранив правиловый экстрактор как запасной путь.
6. **Достроить контур безопасности** из раздела 4.

## 7. Стек: что и почему

Изначально предполагался FastAPI и фронтенд на Tailwind. В процессе
сборки выбран более узкий вариант — стандартная библиотека Python плюс
рукописный CSS. Причины:

* **Офлайн-требование распространяется и на интерфейс.** Tailwind через CDN
  перестаёт работать без интернета, а в зале суда его может не быть.
* **Ноль зависимостей — преимущество для закрытого контура**, где установка
  пакетов из внешних репозиториев часто просто запрещена.
* **Логика от фреймворка не зависит.** Если понадобится OpenAPI-схема,
  готова точка входа `app_fastapi.py`: те же вызовы `core/`, ~60 строк.

Практический эффект: демо разворачивается одной командой `python3 app.py`
на любой машине с Python, без интернета и без прав администратора.
